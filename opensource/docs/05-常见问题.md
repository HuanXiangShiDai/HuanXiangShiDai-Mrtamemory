# 05 · 常见问题

这一章全部来自实际踩过的坑。每条都是 **Q（现象）→ A（原因）→ 怎么查（命令/看哪个数）**。
不确定的地方会写"未验证"，不编。

先约定：下面的 `out/demo.db` 指 01 里建的那个库；`con = huanzao.db.connect(...)` 指
Python API 的连接。

## Q1 为什么我加了很多语料，召回还是空的？

**A**：按可能性从高到低，有五种：

1. **这句话里的词，图上没有对应的元素。** 召回不是全文搜索，入口只有元素。
   比如图里抽到的是"旧伞"，你问"伞修好了吗"——只有单字"伞"，命中不了。
2. **元素 `df=0`。** 没有任何记忆引用它，命中它等于命中空气（公理 P2）。
3. **元素太泛，被 0.30 的泛词线挡了。** 它占全部记忆的 30% 以上，当种子会翻出一堆
   不相干的往事。注意这条线只在 `total >= 4` 时启用。
4. **词在噪声表/机制词表里。** "在吗""记忆""规则"这类词故意不当种子。
5. **刚刚 ingest 的新词，首轮必然 0 命中。** 这是设计（公理 P1），见 Q2。

**怎么查**：

```bash
python -m huanzao.cli recall --db out/demo.db --text "你那句话" --json
```

看 `hits` 数组：

- `hits` 为空 → 卡在第 1/3/4 条，换一个"图上有"的词问；
- `hits` 有值但 `results` 为空 → 卡在可达性闸门（跑 Q11 的检查）。

再查这个元素的 df：

```sql
SELECT n.body, d.df, d.total, ROUND(1.0 * d.df / d.total, 3) AS share
FROM derived_df d JOIN nodes n ON n.id = d.node_id
ORDER BY d.df DESC LIMIT 20;
```

`share > 0.30` 且 `total >= 4` 的元素，注定当不了种子。

## Q2 为什么新建的元素第一次问它，一条都召不回？

**A**：正常，不是 bug。新建元素还没有任何 `has` 边（没有记忆引用它），`df=0`。
召回时命中它，贡献恒为 0；它的价值在 `mentioned` 锚和 `seq` 边上，供以后用。

实测：`咖啡` 建点后 `df=0`，紧接着问"我说起咖啡"，命中 0 条；第二次、并且已经有记忆
引用它之后才会有结果。

**怎么查**：

```sql
SELECT n.id, n.body, COALESCE(d.df, 0) AS df
FROM nodes n LEFT JOIN derived_df d ON d.node_id = n.id
WHERE n.kind IN ('entity','affect') AND n.body = '咖啡';
```

`df=0` 就对了。这不是要调参数，是要再喂一段真的提到它的话。

## Q3 为什么问某个角色名，什么也想不起来？

**A**：角色名在这张图里天生"占得宽"。全是同一个角色群的语料时，某个人名可能出现在
**54%** 的记忆里——远超 0.30 的泛词线，于是被当成背景词挡掉。

但引擎有一条退路：**没有锐词时，交出"最不泛"的一到两个当种子**。所以：

- 如果这句话里还有别的锐词（具体事件、地点、物品），能召回；
- 如果整句只有人名 + 泛词，可能空；这是"宁可这一轮想不起来，也不翻一段不相干的往事"
  的取舍，不是故障。

**怎么查**：

```sql
SELECT n.body, d.df, d.total, ROUND(1.0 * d.df / d.total, 3) AS share
FROM derived_df d JOIN nodes n ON n.id = d.node_id
WHERE n.body IN ('角色甲', '角色乙') ORDER BY share DESC;
```

`share` 超过 0.30 就是背景词。**0.30 是硬线**（`retrieve.hit_elements`），调它要改代码，
不是改规则。想让它想起来，问句里带一件具体的事，而不是只问"某某是个什么样的人"。

## Q4 问"在吗""你好"为什么永远空？

**A**：这两类话在 `NOISE` 表里，命中也不当种子。它们谁都能配上，配上也没用。
同理，"记忆""规则""上下文"在 `META` 表里——谈系统时不翻旧账，这是有意的。

**怎么查**：

```bash
python -m huanzao.cli recall --db out/demo.db --text "你在吗" --json
```

`{"hits": [], "results": []}` 就是对的。不要为了让它有反应去删噪声表，那会把
"在吗"和几百条记忆连起来。

## Q5 设定卡明明在图里，为什么正问问不到？

**A**：设定卡（canon 卡）**不抽元素**，入边只有 `innate`（直挂中心），出边只有 `next`。
三路召回全以元素为入口，所以它在图上是"只进不出的叶子"，**元素边 0 条就永远翻不到**。
实测：53 张卡在补 `topic` 键之前，0 张能被召回；补了 242 条 `topic` 边之后，53 张全有入口。

头段也不是万能：`常驻取舍.innate` 只给前 N 个名额（默认 14，主图调到 24），
超出的卡在图上但读取路径不到。

**怎么查**：

```sql
-- 这张卡有没有 topic 键
SELECT COUNT(*) FROM edges WHERE src = (SELECT id FROM nodes WHERE uniq='canon|demo|core')
  AND rel='topic';
-- 头段到底取了几条 innate
SELECT COUNT(*) FROM edges e JOIN nodes n ON n.id=e.dst
WHERE e.rel='innate' AND n.kind='mem';
```

`topic=0` 且不在 `innate` 前 N 条里 → 问不到。解法：手工加 `topic` 边（键要"可指认"：
人名、地名、事件名，别用"爱""性格"这种抽象词），或者调大 `innate`（头段会变长，
每轮都付 token）。

## Q6 头段每个字都没改，为什么缓存还是报废了？

**A**：头段指纹不是"看起来一样"，是**逐字节的哈希**。任何一处变了都会换指纹：

1. 图变了（加了 `innate` 卡、改了 `常驻取舍`、人格修订切了 `supersedes`）；
2. **排序里掺了会变的东西**。头段的【我知道】必须只按 `innate` 边的建立顺序取；
   曾经按激活值排，结果每轮都可能不同、指纹天天变、前缀全废。

**怎么查**：

```python
from huanzao import db, prompt
con = db.connect("out/demo.db")
a = prompt.build_head(con)
b = prompt.build_head(con)
print(len(a), prompt.digest(a))
print(len(b), prompt.digest(b))   # 两次必须一模一样
```

两次指纹不同 = 有东西在漂。查 `prompt.build_head` 的排序来源，不要查缓存层。

## Q7 我改了规则正文，为什么不生效？

**A**：三个常见原因：

1. **改的是锚点，读的是 `current`。** 有版本之后，生效的是 `current` 边指向的版本，
   不是 `rule|X` 锚点。
2. **直接 `UPDATE nodes.body`。** 版本链、`rulelog`、`audit` 全对不上；
   `rules.ensure_all()` 只补不改，救不回来。
3. **新正文解析不动。** `set_rule` 会先 `parse_body`；解析失败直接抛错，不会写进图。

**怎么查**：

```python
from huanzao import db, rule_graph
con = db.connect("out/demo.db")
print(rule_graph.current(con, "上下文预算"))
print(rule_graph.current_version(con, "上下文预算"))
print([(x["ver"], x["polarity"], x["current"]) for x in rule_graph.history(con, "上下文预算")])
```

`current` 和你以为的不一样 → 指针问题；`current` 一样但行为没变 → 读规则的代码路径
没走到（用 `grep` 找这个键的读者）。

## Q8 回放折块为什么永远说"没有出窗的对话"？

**A**：`turns.ingest` 收完原文默认会 **`DELETE FROM evicted`**，紧接着的 `fold_evicted`
只能拿到空表。这是踩过的坑，修法是两步都看见同一批对话：`consume=False`。

`replay.replay()` 现在内部已经这么调了；如果你自己拼流程，记得传：

```python
from huanzao import db, replay, turns
con = db.connect("out/demo.db")
turns.ingest(con, "evicted", consume=False)   # 先存档，不清源表
replay.replay(con)                             # 再折块
```

**怎么查**：

```sql
SELECT COUNT(*) FROM evicted;
SELECT COUNT(*) FROM mem_src WHERE provenance LIKE '%evicted%';
```

前者 0、后者也不涨，就是被提前清空了。

## Q9 时间轴为什么是空的？"昨天聊了什么"答不出来？

**A**：先分清"没建"和"没东西可建"。`when` / `at` 边只对**"现在"段**（`order_key` 以
`3:` 开头）生效；往事用叙事坐标（段:章:行），没有日历可对。

如果库里一条"现在"段的记忆都没有，`day` 节点本来就该是 0 个——不是时间轴坏了。
实测：某张主图 423 段全是往事，day 节点 0，补进 74 条"现在"段后才有 8 个 day、73 条 `when`。

**怎么查**：

```sql
SELECT COUNT(*) FROM mem_src WHERE order_key LIKE '3:%';        -- 现在段有几条
SELECT COUNT(*) FROM mem_src WHERE when_iso = 'canon';          -- 设定卡几条
SELECT COUNT(*) FROM nodes WHERE kind = 'day';                  -- 日期节点几个
```

`3:%` 为 0 → 没东西可建，先喂"现在"的事（CLI 的 `ingest` 就写 `3:` 段，所以新库不会有
这个问题）。

## Q10 骨干为什么不是 87 个？我该信哪个数？

**A**：**一个图一个数，别写死。** 87 是旧图（924 条记忆）算出来的；同一套集合覆盖算法
在新图（423 条）上实需 33 个，接完"现在"段后是 47 个。数字变了不是算法坏了，是图和
覆盖目标变了。

开源 CLI 每次 `ingest` 后用 `grow.link_backbone(con, 24)` 重算一次骨干——24 是**默认
k 上限**，不是"最优值"。

**怎么查**：

```python
from huanzao import db, grow
con = db.connect("out/demo.db")
els = grow.backbone(con, k=120)          # 贪心集合覆盖
print(len(els), els[:10])
print(grow.eccentricity(con, con.execute("SELECT id FROM nodes WHERE kind='center'").fetchone()["id"]))
```

`eccentricity` 的 `mem_ecc` 就是"最远的记忆几跳"。骨干的作用是把它压到 ≤3；
如果 `unreachable` 很大，才需要重算骨干，而不是把 k 调大。

## Q11 离心率恒等于 1、中心闸门什么都不拦，是怎么回事？

**A**：十有八九是 **`about` 边被当成了路**。重建脚本可能给每条记忆都挂了一条
`mem --about--> center`；代码里没人读它，但一量距离，每条记忆都离中心 1 跳，
于是"≤4 跳"的闸门永远放行，骨干选谁都一样。

修法不是删边（只增不改），是量距离时跳过它：`grow.SKIP_RELS = ("about",)`，
`diffuse._hops_from_center` 也跳过 `about` / `view`。

**怎么查**：

```python
from huanzao import db, grow
con = db.connect("out/demo.db")
center = con.execute("SELECT id FROM nodes WHERE kind='center'").fetchone()["id"]
print(grow.eccentricity(con, center))
# {'mem_ecc': 2, 'all_ecc': 3, 'unreachable': 0, 'reached': ...}
```

`mem_ecc=1` 且图里到处是 `about` 边 → 就是这个坑。正确的记忆离心率通常是 2。

## Q12 为什么规则版本节点在离心率统计里"到不了中心"？

**A**：有意的。规则版本节点和 `rulelog` 不连中心，实测 397 个在可达性统计里算"到不了"。
规则靠**名字解析**找到生效版本（`rule_graph.current`），不靠结构可达。把它们连进中心，
等于让"规则"参与"记忆"的扩散，会把检索的语义搅浑。

**怎么查**：

```sql
SELECT COUNT(*) FROM nodes WHERE kind='rule' AND uniq LIKE 'rule|%|v%';
SELECT COUNT(*) FROM edges WHERE rel='backbone' OR rel='innate' OR rel='axis';
```

版本节点数在涨、到不了中心，是正常状态；不要为了"离心率好看"去补边。

## Q13 思考写进图之后，脉冲（激活）全是废词，怎么办？

**A**：两个坑，修法都在代码里：

1. **不筛虚词**：思考是散文/代码混排，"一半""一句""一次"会被当成元素抬进激活层，
   top10 全是废词。现在 `thought._elements_in` 用与召回同一张跳过表（NOISE/META/
   操作词/话题词），并且 **`df=0` 直接跳过**。
2. **思考灌顶**：92 条思考每条按满额抬 14 个元素，一秒全员封顶 3.0，脉冲失去分辨力。
   现在一条思考只抬**最锐的 3 个元素**（df 最小），幅度减半。

**怎么查**：

```python
from huanzao import activation, db
con = db.connect("out/demo.db")
print(activation.values(con))     # 应该是少数几个高值，不是全员 3.0
```

一大片 3.0 = 灌顶；top 全是"一半""一句" = 没筛虚词。

## Q14 注入的记忆块，怎么被当成"他说的话"折进记忆了？

**A**：注入块没有包标记，或者包了但回放侧没认出来。回放折块只该折"他说的话"，
注入块是脚手架（公理 A6：折块算子 `D(I)=0`）。现成的闸是 `turns._strip_own`，它认两种标记：

```text
〔记忆注入｜脚手架·不是他说的〕 … 〔／记忆注入〕
【此刻浮上来的】 …（这些是你心里浮上来的
```

**怎么查**：

```sql
SELECT mem_node, substr(raw, 1, 60) FROM mem_src WHERE raw LIKE '%记忆注入%';
SELECT mem_node, substr(raw, 1, 60) FROM mem_src WHERE raw LIKE '%此刻浮上来的%';
```

有结果 = 注入被折进去了。检查写入路径有没有在 `_strip_own` 之前就把块拼进原文。

## Q15 单字的人名 / 单字情绪词，为什么一个能用一个不能用？

**A**：抽取时元素默认至少 2 个字；**情绪词豁免**，单字也算（累、笑、哭、怕）。
单字人名在元素召回里会被"至少两个字"挡住，但在**设定卡的 `topic` 键**里放行
（`cards_for_text` 对 `view.NAMES` 里的单字名有例外），否则关系卡会没有键。

**怎么查**：

```sql
SELECT id, kind, body FROM nodes WHERE LENGTH(body) = 1;
```

只有 `kind='affect'` 的单字是元素；单字人名如果要以"可指认的键"存在，应该在
`topic` 边上，不是 `has` 元素。

## Q16 "十一月十七号我们说过什么"为什么解析不出日期？

**A**：老版本只认阿拉伯数字日期（`11月17号`）。现在 `times.parse` 补了中文数字
（一/十/十一/二十三），但**中文秒**仍不认（"二十三秒"不行，"23秒"可以）。
另外，日期解析出来只是"过滤器"，那天没有记忆时**不动候选**——不能因为日期空了就
把整句的命中清掉。

**怎么查**：

```python
from huanzao import frame, times
print(times.parse("十一月十七号我们说过什么"))
print(frame.judge("十一月十七号我们说过什么"))
```

`days` 为空 = 没解析出来；`days` 有值但召回空 = 那天没有记忆，或被日期过滤器挡了。

## Q17 工程对话被 ingest 进去了，她开始记得"改代码"了，怎么办？

**A**：`rule|不入记忆` 那张词表（46 个工程词）**只有 `replay` 在读**：命中 ≥2 个词才算
工程，折块时跳过。**`ingest` 不调它**——开源版的 ingest 是"你给什么就收什么"，
工程过滤是人工纪律，不是闸门。

**怎么查**：

```python
from huanzao import db, rules
con = db.connect("out/demo.db")
print(rules.is_engineering(con, "把缓存层改一下，重新跑一遍测试"))
# True：这句话会被 replay 挡，但 ingest 不会挡
```

已经进去的工程记忆只能人工清理（或重建库）。预防靠两条：喂之前自己过一遍；
把工程词补进 `rule|不入记忆`（它会被 `replay` 读到）。

## Q18 元素抽得太碎/太泛，怎么办？

**A**：规则抽取对自传体散文的质量有限。实测：一段"我当时心里想……"会被抽出
"当时心里"（63 段）、"十一月十""半左右"这种碎片。这不是调参能解决的，是抽取器的
能力边界。

三条现实选择：

1. **闭词表**：只认图里已经有的元素（`flow.elements_in_order` 的做法），新词不建点；
2. **把话说具体**：喂"我们在城北旧书店躲雨"，比喂"那段时间我心里很乱"抽得准；
3. **换 LLM 抽取**：`extract.run(text, "llm")` 有接口，但开源版默认走规则抽取
   （离线、确定性、零成本）。

**怎么查**：

```sql
SELECT n.body, d.df FROM derived_df d JOIN nodes n ON n.id=d.node_id
ORDER BY d.df DESC LIMIT 30;
```

排在前面的如果全是"当时心里""天晚上""半左右"，就是抽取质量的问题；
它们还会挤占头段的【常在我心上的】，所以头段渲染时额外跳过了时间词和"心里想"开头。

```bash
python -m huanzao.cli status --db out/demo.db

python -m huanzao.cli remind --db out/demo.db --text "你那句话" --limit 0
```

- `status` 看四项计数有没有长；
- `recall --json` 看 `hits`（入口有没有命中）和 `results`（闸门有没有放行）；
- `remind --limit 0` 看原文到底被取出来没有（排除截断导致的"看起来空"）。

再往下才是 SQL 和 Python API。**先确认入口，再怀疑参数**——这张图里九成"召不回"
是入口不存在，不是排序不对。

## Q19. 我把触发规则改了，为什么它还按老条件触发？

因为读的是**锚点正文**，不是**生效版本**。锚点永远留着最初那条 body，
改过之后生效的是 `rule|触发·放宽|v1`。

修法：任何"读规则"的地方都走 `current()`。开发时踩过两次——
改完不生效，等于没改。

诊断：
```bash
python -m huanzao.cli rule history --name 触发·放宽   # 看有没有 v1
```

## Q20. 我的元触发被普通触发抢了命中，怎么办？

`match()` 必须**按命中词的长度降序**返回。文本「去掉「放宽」这个触发条件」里
同时含「多记」（2 字）和「这个触发条件」（6 字）；按 id 顺序会先命中「放宽」，
元触发永远轮不到，环就合不上。

修法：命中的词越长越锐，越该优先。

## Q21. 为什么 stop+ 删不掉触发规则里的触发词？

`stop±` 原本只认**词表型**正文（一整列词）。触发规则的触发词藏在 kv 型的 `when` 里，
所以必须带键：`payload = {"key": "when", "w": "多记"}`。

另外：**不能把 when 删空**。删到最后一个词等于废掉这条规则——
那该用 `supersedes` 明说，而不是偷偷 `stop+` 抹掉。
